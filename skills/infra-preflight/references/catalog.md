# Infrastructure Trap Catalog

One trap per block. Only real production traps enter this catalog, along with their origin. Format: **Symptom** (what you observe), **Cause** (why it happens), **Test that catches it** (what to run before merge or during pre-flight), **Origin** (generic, no project name).
Project-specific facts (paths, UIDs, scripts, `L1..Ln` local traps) belong in the project's `docs/infra.md`, not here.

---

## C1. Bind-mounted config changes on disk while the container keeps the old config

- **Symptom:** Deploy finishes green, the updated file is on the server's disk, yet the service continues running with the old behavior until someone manually recreates the container.
- **Cause:** `docker compose up -d <service>` only recreates a container when the service **definition** changes (image, env, labels, command, declared mounts). The contents of a bind-mounted file are not part of the service definition. Some services hot-reload config on their own; most read it once at boot.
- **Test that catches it:** For every mounted file modified by the PRD, answer "how does this change reach the running process?". Cheap fix: embed the file's SHA-256 hash in a service label or env var (`sha256sum <file>` exported before `up`), changing the service definition whenever file contents change. Test: run `compose config` against two different file contents and assert the rendered labels differ; post-deploy, compare the container ID before and after.
- **Origin:** Log collector config hotfix remained inactive for ~3.5 hours after deploy (2026-10).

## C2. File permissions pass on macOS and fail on Linux

- **Symptom:** A test that bind-mounts a file into a container passes on macOS and fails in CI with `permission denied`.
- **Cause:** Docker Desktop on macOS serves mounted files without enforcing host owner and mode bits. On Linux, mode bits are strictly enforced: pytest's temporary directory (`tmp_path`) is created with `0700`, so a container running under a different UID (e.g., `nobody`) cannot traverse or read it.
- **Test that catches it:** Run the container with `--user "$(id -u):$(id -g)"` matching the host, or prove readability with the file inside a `0700` directory; execute the test suite in a Linux environment with a non-root UID before spec review (`SKILL.md`, Section 3).
- **Origin:** Containerized alert-rule validator broke CI and skipped 1 deploy (2026-10).

## C3. Host agent lacks permission to read collected logs or write its own state

- **Symptom:** The collector starts without an obvious crash, but zero data reaches the destination; or it halts when attempting to persist its read cursor.
- **Cause:** Docker container logs (`/var/lib/docker/containers/<id>/*-json.log`) are owned by `root` inside a restricted directory; a non-root container cannot read them. Meanwhile, the state volume is owned by the user defined in the **base image**, which can differ from the `user:` override in compose. Security hardening (`cap_drop: [ALL]`, `read_only`) drops `CAP_DAC_OVERRIDE`, which previously masked permission mismatches when running as root.
- **Test that catches it:** Pre-flight check with `stat` on host paths and `docker compose exec -T <service> id`; integration test that starts the real image with the compose `user:`, mounts a root-owned restricted directory, and asserts both log reading and state cursor persistence.
- **Origin:** Log collector shipped to production emitting zero data on activation (2026-10).

## C4. Cron supervisor re-wraps job output

- **Symptom:** The scheduled job runs and its output appears in container logs, but the downstream consumer (collector, alert rule, parser) fails to recognize the event; "missing job" alerts fire while the job is healthy.
- **Cause:** Container cron supervisors capture the job's stdout/stderr and re-emit each line wrapped in their own envelope. By default, Supercronic wraps every job line in `time=… level=info msg=… channel=stderr`; only `-passthrough-logs` emits raw lines. A parser expecting `{` at column 0 drops the wrapped line.
- **Test that catches it:** Pre-flight `logs --tail` on the real cron service to inspect the exact emitted line format; feed the parser test with lines **as emitted by the supervisor**, not raw application lines.
- **Origin:** False-positive "job missing" alerts firing for 3 healthy cron jobs (2026-10).

## C5. Synthetic test fixture uses a format the real producer never emits

- **Symptom:** Consumer unit tests pass green; in production, the consumer rejects every real input.
- **Cause:** The test fixture was hand-typed rather than generated by the producer. Example: consumer regex requires a hyphenated UUID (`8-4-4-4-12`), while the producer emits `uuid4().hex` (32 hex chars, no hyphens). The test and consumer agree with each other and disagree with reality.
- **Test that catches it:** Contract test at every cross-process boundary: generate the fixture by calling the producer's real serializer function (or copy a verbatim line captured during pre-flight), never by typing a synthetic string.
- **Origin:** Same incident as C4; the two root causes were independent and either one alone would have dropped the logs (2026-10).

## C6. Scheduled jobs overlap on the same database table

- **Symptom:** A long-running job dies repeatedly with a database deadlock (`40P01` in Postgres); writes stall for hours.
- **Cause:** A change allowed distinct writers to run concurrently (per-resource lock instead of a global lock, or new cron schedules). Deadlock analysis checked only file/process locks, ignoring the order in which each writer locks **rows** in the database. Two writers locking overlapping row sets in opposite orders deadlock.
- **Test that catches it:** The PRD lists every writer touching the resource and their overlapping windows (using measured real duration, not nominal schedule); integration test runs 2 real writer processes concurrently against a real database updating the same set in opposite orders. Standard fix: serialize the unit of write (`pg_advisory_lock`) and retry only on `40P01` with a bounded retry count.
- **Origin:** Ingestion job stalled for ~27 hours before detection (2026-10).

## C7. CI context variable is empty on specific trigger events

- **Symptom:** A CI step that diffs against the previous commit breaks on a specific push (new branch, manual dispatch) while passing on normal pushes.
- **Cause:** `github.event.before` is only populated on `push` events; it is all-zeros on the first push of a new branch and empty on `workflow_dispatch` and `schedule`. On `pull_request`, the base commit lives at `github.event.pull_request.base.sha`.
- **Test that catches it:** For every trigger listed under `on:` in the workflow, document the context variables used and their value under each event type; the script must handle empty and all-zero SHAs explicitly (skip with a clear log message rather than crashing or silently passing).
- **Origin:** Migration round-trip check failing in CI on branch creation and manual runs (2026-09).

## C8. Service behind `profiles:` never starts during deploy

- **Symptom:** Deploy finishes green, yet the service never runs (e.g., cron service executes nothing after launch).
- **Cause:** A service with `profiles: [...]` in compose is ignored by `up`, `build`, and `config` unless `--profile` (or `COMPOSE_PROFILES`) is explicitly passed. No error is emitted. Exception: commands that explicitly name the service (`up <service>`) auto-enable its profile for that service and its `depends_on` ([Docker docs](https://docs.docker.com/compose/how-tos/profiles/#auto-starting-profiles-and-dependency-resolution)). Unscoped commands (`up -d`, `build`) silently skip it.
- **Test that catches it:** Static workflow test asserting `--profile <name>` on every compose command intended to touch the service; post-deploy verification checks `compose ps` for the service in `running` state.
- **Origin:** Full product launch went live without its background ingestion service running (2026-09).

## C9. SSH heredoc: inner command reading stdin swallows the rest of the deploy script

- **Symptom:** Deploy finishes with exit code 0, but commands after a specific line never executed (the old container stays running).
- **Cause:** In `ssh host 'bash -s' <<'EOF' … EOF`, the script is piped into `bash` via stdin. Any inner command that reads from stdin (`psql`, `docker exec -i`, `read`, `ssh`) consumes the remaining lines of the script; `bash` hits EOF and exits 0.
- **Test that catches it:** Redirect stdin from `/dev/null` (`< /dev/null`) on every command inside an SSH heredoc that could read stdin; end the deploy script with a positive assertion (container recreated, new container ID, image matches expected SHA) that fails loudly if skipped. Static workflow test enforces `< /dev/null` and the trailing assertion.
- **Origin:** Green deploy that failed to recreate the API container, repeating the same failure class 20 days later (2026-09).

## C10. Newly declared volume does not preserve data written to the old container's writable layer

- **Symptom:** After deploying a compose file that adds a persistent volume mount, the service comes up with an empty history.
- **Cause:** The volume exists only in the new service definition; the running container wrote its files to its ephemeral writable layer. Recreating the container mounts a fresh empty volume over that path and orphans the data in the old container layer.
- **Test that catches it:** Selective `docker inspect` of active mounts on the target before running `up`; abort if the existing container lacks the volume at the target path. Rehearse migration with real producer data: stop writer, copy all active and rotated files out of the container layer, record inventory/byte counts/SHA-256 hashes, recreate container without starting, restore files into the volume, and verify hashes before starting; any copy/hash failure must abort container replacement. Verify new writes land in the volume and all other volumes remain intact.
- **Origin:** Persistence configuration shipped to host while existing container lacked the mount and held logs only in its writable layer (2026-11).
